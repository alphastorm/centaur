# Using the OMP Harness

Centaur can run [oh-my-pi](https://github.com/can1357/oh-my-pi) (OMP) as a
session harness alongside Codex, Claude Code, Amp, Nanocodex, and Hermes.
Start a Slack, GitHub, or Linear thread with `--omp` (or set `omp` as a channel
or deployment default) and the sandbox runs a long-lived `omp --mode rpc`
process for that thread instead of a spawn-per-turn CLI.

## How the integration works

- **One OMP process per thread** — `harness-server omp` speaks OMP's RPC
  protocol over stdio and keeps the process alive across turns. Steering
  appends to the active turn; an interrupt sends OMP `abort` and only kills
  the process if the turn does not end within the grace period.
- **Native session resume** — each thread gets its own OMP session directory,
  `$CENTAUR_OMP_SESSION_ROOT/<sha256(thread key)>`, and OMP starts with
  `--session-dir <dir> --continue`. If the OMP process exits, the next turn
  starts it again on the same directory and OMP continues the conversation.
  History survives a sandbox replacement only when that directory is on
  persistent storage.
- **Turn completion** — OMP 18.3 terminal events carry no prompt id, so a turn
  completes only after its own `agent_start`, a terminal `agent_end`, and a
  `get_state` response reporting that OMP is no longer streaming. Late or
  duplicate terminal events from an earlier turn are ignored. Unknown event
  kinds fail the turn instead of being dropped.
- **Errors** — a provider error that OMP does not retry ends the turn as
  failed with the provider's error line; OMP's own retries continue the turn.
- **Host callbacks** — a sandbox has no interactive host, so OMP host tool,
  host URI, and interactive UI requests are declined; presentation-only UI
  updates are ignored.

## Configuration

| Variable | Purpose |
|---|---|
| `CENTAUR_OMP_BIN` | `omp` executable (default: `omp` on `PATH`). |
| `CENTAUR_OMP_SESSION_ROOT` | Root for per-thread session directories (default: `~/.omp/centaur-sessions`). |
| `CENTAUR_THREAD_KEY` | Set by the session runtime; selects the thread's session directory. Without it, `harness-server omp` starts a new thread. |

The sandbox image installs `@oh-my-pi/pi-coding-agent` 18.3.0 from a frozen
lockfile (which needs Bun 1.3.14 or newer) and checks the installed version at
build time. OMP uses its stock tools and settings. When a sandbox state volume
is mounted, the entrypoint keeps `~/.omp` on it next to the other harnesses'
state.

OMP cannot be the warm-pool harness: api-rs refuses to start with
`SESSION_SANDBOX_HARNESS=omp` and a nonzero `SESSION_SANDBOX_WARM_POOL_SIZE`,
because warm sandboxes boot before their thread key is known.

## Models and credentials

Select a model with `--model provider/model`, for example
`--omp --model anthropic/claude-sonnet-4-5`; without one, OMP uses its default.
OMP reads provider keys from its environment the stock way. In a managed
sandbox those variables hold placeholders, and iron-proxy swaps in the real
credential on egress for every provider with a registered fragment: Anthropic
through the Claude Code fragment (`CLAUDE_CODE_AUTH_MODE`), OpenAI through the
Codex fragment, and the other fragments api-rs registers for every harness.
Any other provider needs its own fragment or overlay, as with the other
harnesses.

## Rollback

Migration `0056` adds `omp` to the sessions harness constraint and is
forward-only. To stop using OMP, stop selecting it; keep the migration applied
and keep rows with `harness_type = 'omp'` while older readers could see them.
